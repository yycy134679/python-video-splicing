# 落版视频上传与持久化设计

## 1. 背景

当前“视频拼接”页使用固定的落版视频路径 `SP_ENDCARD_PATH`。当市场部提供新的落版视频时，只能通过修改程序配置或替换项目内文件来生效，业务同学无法在页面内自行更新。

这带来三个直接问题：

- 落版更新依赖开发修改代码或重新配置环境。
- 当前生效的落版视频在页面中不可见，业务同学无法直接确认。
- 重新上传与切换落版缺少稳定、持久化的管理入口。

## 2. 目标

- 允许业务同学在“视频拼接”页上传落版视频文件。
- 上传后的落版视频持久化保存，页面刷新和应用重启后继续生效。
- 页面中可查看当前生效落版的文件信息，并可直接预览。
- 支持重新上传新的落版视频，新文件覆盖旧文件并立即对后续新任务生效。
- 首版支持上传 `mp4` 和 `mov` 两种格式。

## 3. 非目标

- 不支持同时保留多个历史版本。
- 不支持在页面内切换回旧版本。
- 不支持按用户、按批次或按浏览器会话隔离落版配置。
- 不在首版中增加视频裁剪、封面提取、手动转码等扩展能力。

## 4. 当前现状

- `video_splicer.config.load_config()` 当前直接读取 `SP_ENDCARD_PATH`，默认指向仓库内的 `assets/video/endcard.mp4`。
- `validate_splice_runtime()` 仅校验当前 `endcard_path` 是否存在。
- `video_splicer.runner._process_single_splice()` 在任务执行时直接使用 `config.endcard_path`。
- `app.py` 当前没有“落版视频管理”区，也没有用于持久化上传文件的模块。

这意味着现有拼接链路已经具备“消费一个落版视频路径”的能力，缺的是“如何得到当前稳定可用的落版路径”以及对应的页面管理入口。

## 5. 方案对比

### 方案 A：受管落版存储（推荐）

新增一个受管落版目录，由应用负责保存当前生效的落版文件。配置层优先读取该目录中的当前文件；若用户尚未上传，则回退到现有默认落版 `assets/video/endcard.mp4`。

优点：

- 与当前拼接链路最兼容，核心处理流程基本无需感知上传能力。
- 支持页面刷新、应用重启、打包后运行等场景。
- 便于后续扩展，但当前实现仍保持简单。

缺点：

- 需要新增一层很薄的文件管理逻辑。

### 方案 B：直接覆盖仓库内默认落版文件

上传后直接替换 `assets/video/endcard.mp4`。

优点：

- 改动最少。

缺点：

- 打包后的 `.app` 或只读目录可能无法写入。
- `mov` 与 `mp4` 混用时文件命名与资源组织不自然。
- 业务上传文件与项目静态资源耦合，后续维护风险高。

### 方案 C：存储文件并额外维护配置文件

上传文件保存到固定目录，再用单独的 `json` 或 `toml` 配置文件记录当前生效路径和元数据。

优点：

- 结构清晰，后续扩展历史版本或多套落版更方便。

缺点：

- 对“只保留一个当前版本”的需求来说偏重，超出当前必要范围。

## 6. 决策摘要

选择方案 A：受管落版存储。

核心决策如下：

- 只保留一个“当前生效”的落版视频。
- 落版视频采用应用级本地持久化，而不是浏览器会话级状态。
- 拼接页顶部新增“落版视频管理”区。
- 上传成功后立即覆盖当前落版并生效，不再增加“设为当前”步骤。
- 新上传只影响后续新发起的拼接任务，不影响已经开始执行的批次。
- 如果用户从未上传过落版，则继续使用现有默认落版视频。

## 7. 详细设计

### 7.1 存储与命名

新增受管目录，例如：

```text
~/.video-splicer/endcard/
```

目录中只保留一个当前文件，统一使用稳定文件名前缀：

- `current-endcard.mp4`
- `current-endcard.mov`

保存新文件前，先清理该目录下旧的 `current-endcard.*` 文件，再写入新的当前文件。这样不需要额外维护复杂配置文件，也能稳定定位当前生效文件。

### 7.2 配置解析

`Config.endcard_path` 的解析规则调整为：

1. 若受管目录中存在当前落版文件，则优先使用该文件。
2. 若不存在，则回退到现有默认落版 `assets/video/endcard.mp4`。

`SP_ENDCARD_PATH` 仍可保留作为兼容入口，但页面内上传能力不再依赖用户手工修改该环境变量。首版建议页面逻辑始终以“受管目录优先、默认文件兜底”为准。

### 7.3 新增模块职责

建议新增 `video_splicer/endcard_store.py`，职责保持单一，只负责：

- 定位受管落版目录。
- 查找当前生效落版文件。
- 提供默认落版回退路径。
- 保存上传文件并覆盖旧文件。
- 读取当前落版的展示信息，如文件名、格式、大小、最后更新时间。

该模块不负责页面渲染，不负责拼接流程，不负责结果产物保存。

### 7.4 上传与生效流程

页面交互建议为：

1. 用户在“视频拼接”页顶部选择一个 `mp4` 或 `mov` 文件。
2. 用户点击一次性动作按钮“上传并立即生效”。
3. 服务端先把文件写入临时路径。
4. 使用现有 FFmpeg/FFprobe 能力探测该文件，确认其是可读取的视频。
5. 校验通过后，原子性替换受管目录中的当前落版文件。
6. 页面刷新当前状态，提示“新落版已保存，后续新发起的拼接任务将使用该文件”。

这里的“立即生效”定义为：对上传成功后的后续新任务立即生效，而不是中途切换已经开始执行的任务。

### 7.5 页面结构

在“视频拼接”页顶部、数据输入区上方新增一个独立的“落版视频管理”区，包含：

- 当前生效状态说明。
- 当前文件名。
- 当前文件格式。
- 当前文件大小。
- 最后更新时间。
- 当前文件视频预览。
- 上传控件。
- “上传并立即生效”按钮。
- 上传成功或失败提示。

如果当前使用的是默认落版文件，应明确展示“当前使用默认落版视频”。如果当前使用的是用户上传文件，应展示“当前使用已上传落版视频”。

### 7.6 预览策略

首版使用“文件信息 + 页面内视频播放”作为预览能力：

- 文字信息用于确认当前到底用了哪一个文件。
- `st.video` 用于直接预览当前生效落版内容。

重新上传成功后，预览区域直接切换到新文件，不保留旧版本对比或历史记录。

### 7.7 运行时行为

拼接任务保持当前模式：任务开始时读取一次 `config.endcard_path`，后续整个批次都使用这一份路径。

因此：

- 批次 A 开始后，即使用户重新上传了新落版，批次 A 仍继续使用旧路径。
- 用户在批次 A 执行过程中上传新落版，只会影响后续新发起的批次 B、C。

这样可以避免并发任务在处理中途切换落版资源，保证同批次行为一致。

## 8. 校验与错误处理

上传链路按以下顺序校验：

1. 文件是否存在。
2. 扩展名是否为 `mp4` 或 `mov`。
3. 上传内容是否可写入临时文件。
4. FFprobe 是否能成功探测该文件。

校验失败时：

- 返回明确的中文错误信息。
- 不覆盖当前已生效落版。
- 页面继续保留旧落版的文件信息和预览。

推荐错误文案方向：

- `仅支持上传 mp4 或 mov 格式的落版视频`
- `落版视频保存失败：...`
- `无法识别该落版视频，请确认文件未损坏`
- `落版视频校验失败，当前仍使用原有落版`

## 9. 测试策略

按“先补测试，再改实现”的方式推进，重点覆盖以下场景：

- 未上传过自定义落版时，配置层正确回退到默认落版。
- 已存在受管落版时，配置层优先返回受管文件路径。
- 上传合法 `mp4` 文件后，当前落版切换成功。
- 上传合法 `mov` 文件后，当前落版切换成功。
- 上传非法扩展名时，返回错误且不覆盖旧落版。
- 上传损坏视频或无法探测的视频时，返回错误且不覆盖旧落版。
- 重复上传新文件时，旧文件被替换，目录中仅保留一个当前文件。
- 拼接页运行前校验仍能识别当前落版是否存在。

## 10. 实施拆分

为避免一次改动过多文件，按 3 个小迭代推进：

### 迭代 1：落版存储与配置能力

- 新增 `video_splicer/endcard_store.py`
- 调整 `video_splicer/config.py`
- 新增对应单元测试

验收标准：

- 代码可稳定解析当前落版路径。
- 未上传时回退默认落版。
- 已上传时优先使用受管落版。

### 迭代 2：拼接页管理区与预览

- 在 `app.py` 拼接页增加“落版视频管理”区
- 接入上传、预览、成功/失败提示

验收标准：

- 页面可看到当前落版信息与预览。
- 上传后页面状态立即刷新。
- 上传失败不影响旧落版继续可用。

### 迭代 3：测试补齐与 README 更新

- 补齐上传边界测试
- 更新 `README.md`

验收标准：

- 测试覆盖核心边界。
- 文档清楚说明支持格式、默认回退、生效范围与重新上传行为。

## 11. 风险与控制

- 风险：用户上传损坏文件导致当前落版不可用。  
  控制：先写临时文件并探测，校验通过后再覆盖旧文件。

- 风险：批处理中途更换落版导致同批次结果不一致。  
  控制：任务启动时固定读取一次落版路径，上传只影响后续新任务。

- 风险：打包环境中仓库目录不可写。  
  控制：不覆盖项目静态资源，改为写入用户目录下的受管目录。

## 12. 成功标准

当以下条件全部满足时，可认为该需求完成：

- 业务同学无需改代码即可在页面中上传新的落版视频。
- 上传后的落版在页面刷新与应用重启后仍保持生效。
- 页面可以直接预览当前生效落版。
- 重新上传新文件后，后续新拼接任务使用新落版。
- 非法或损坏文件不会破坏当前可用落版。
